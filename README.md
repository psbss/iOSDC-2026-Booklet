# 今どきの画像アセット入稿：たった1枚の画像でアプリサイズが50MB増えた失敗から学ぶ最適化方法
## プロポーザル
fortee: https://fortee.jp/iosdc-japan-2026/proposal/77865922-8ad8-4296-9236-0e3c2a93c424

アプリで利用する画像アセットを追加するとき、「とりあえずPNGを1x〜3xで3枚用意する」「ベクター画像はPDFで入れる」といった判断をしていませんか？

ある日、私も何気なく追加した "たった1枚の画像" によって、アプリサイズが約50MB急増してしまいました。いつものようにFigmaからSVG形式で書き出し、 Assets.xcassets に Preserve Vector Data オプションを有効にした状態で追加しただけでしたが、ついには審査提出時にアプリサイズに関する警告メールが届きました。

原因を追っていくと、問題は「元画像のファイルサイズ」だけではありませんでした。Xcodeがアセットカタログをコンパイルする過程やApp Thinningの影響により、画像形式、圧縮オプション、ベクター保持の有無などで、最終的な Assets.car や IPA サイズは大きく変わることが判明しました。手元のファイルサイズだけでは実際にユーザーへ配信されるアプリサイズへの影響は見えづらいようです。

この記事では、最新安定版であるXcode 26.xを用いて、画像アセットの入稿方法を実測ベースで検証し、結果を元に実務で使える判断基準に落とし込みます。 具体的には、PNG/JPEG/PDF/SVG/HEIF/WebP などの画像形式ごとに、元ファイルサイズ、ビルド後のAssets.carサイズ、IPAサイズを比較し、どのような画像をどの形式・設定で入稿すべきか、PRレビューやCIでどう確認すべきかを整理します。

「アイコンはPDF」「写真ならJPEG」といった経験則は、現在のXcodeでも本当に有効なのでしょうか。 この記事では、アプリサイズをできる限り小さく保ち、初回ダウンロードやアップデート時の負担を増やしにくい、今どきの画像アセット運用を考えます。
